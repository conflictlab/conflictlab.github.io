# Website Refresh & Monitoring Guide

This guide explains how the site updates each month, how to run a full refresh on demand, and how monitoring + email alerts work.

## One‑Click Refresh (Manual)

- Trigger: Actions → "Refresh Website Now" → Run workflow
- What it does (end‑to‑end):
  - Syncs latest national forecast CSVs and PRIO‑GRID assets (centroids, GeoJSON, monthly point JSONs, CSVs, per‑country grids)
  - Exports static API JSON under `public/api/v1`
  - Updates scenarios (download pickle → convert → compute `minmax.json` → write `scenarios.denorm.json`)
  - Updates DTW matches (download pickle → convert to `public/data/matches.json`)
  - Generates `public/status.json`
  - Commits/pushes changes to `main`
  - Triggers deploy to GitHub Pages (via workflow_run)
  - Health check runs after deploy

## Regular Schedules

- 28th (pre-month) and 1st (fallback):
  - 03:00 UTC — Refresh (end‑to‑end): `.github/workflows/refresh-website.yml`
- Deploy to Pages: auto‑runs after refresh completes or on push
  - Workflow: `.github/workflows/deploy-pages.yml`
- Health check (live site): 06:00 UTC on 28th and 1st, and after deploys
  - Workflow: `.github/workflows/health-check.yml`

## Email Notifications

SMTP‑based mail is wired into the workflows. Steps only run if required secrets exist.

Set these repository secrets (Settings → Secrets and variables → Actions):
- `SMTP_SERVER` (e.g., smtp.gmail.com, smtp.sendgrid.net)
- `SMTP_PORT` (465 for SSL, 587 for STARTTLS)
- `SMTP_SECURE` (`true` for 465, `false` for 587)
- `SMTP_USERNAME`, `SMTP_PASSWORD` (use an app password or provider API key)
- `MAIL_FROM` (e.g., `PaCE Bot <bot@yourdomain.com>`) — optional but recommended
- `MAIL_TO` (comma‑separated recipients) — optional but recommended

When emails are sent:
- Success + failure
  - Refresh Website Now: `.github/workflows/refresh-website.yml`
  - Deploy to GitHub Pages: `.github/workflows/deploy-pages.yml`
- Failure only
  - Health check: `.github/workflows/health-check.yml`

Test email:
- Actions → "Test Email" → Run workflow (provide `to`; `from` optional)
- Workflow: `.github/workflows/test-email.yml`

## Status & Health

- Status file: `public/status.json` generated by `scripts/generate-status.js`
- Status page (human‑readable): `/status` → renders `status.json`
  - File: `app/status/page.tsx`
- Live health checker: `scripts/check-live.js` (follows redirects)
  - Validates deployed `/status.json` and a sample static API endpoint
  - Also checks remote CSV metadata freshness (from `app/data-api/page.tsx` base)
- Health Check workflow opens an issue on failure (uses `GITHUB_TOKEN`), and optionally emails (if `MAIL_*` + `SMTP_*` secrets are set)

## Manual Triggers (Individual)

- Refresh Website Now: Actions → "Refresh Website Now"
- Deploy: Actions → "Deploy to GitHub Pages" (auto after refresh)
- Health: Actions → "Health Check (Live Site)"

CLI (optional):
```bash
# Requires GitHub CLI (gh) authenticated
gh workflow run "Refresh Website Now"
```

## Troubleshooting

- No email received
  - Ensure `MAIL_TO`, `MAIL_FROM`, and all `SMTP_*` secrets are set
  - Check the workflow logs: email steps are skipped if secrets are missing
  - Some providers require `MAIL_FROM` to be a verified/allowed address
- "Resource not accessible by integration" when opening issues
  - The health‑check workflow requires `issues: write` permission (already set) and uses `GITHUB_TOKEN`
- Health check fails with 301
  - `scripts/check-live.js` now follows redirects; re‑run Health Check
- Deploy didn’t run
  - Deploy is triggered by `workflow_run` on the other workflows; if running on a fork or with restricted tokens, trigger "Deploy to GitHub Pages" manually

## Configuration

- Change health freshness threshold: edit `.github/workflows/health-check.yml` and pass `--maxAgeDays` to `scripts/check-live.js`
- Adjust early run days/times: edit crons in `update-minmax.yml` and `update-matches.yml`
- Data API base for CSVs: see `app/data-api/page.tsx` (`GITHUB_BASE`)
